# Component Usage Documentation — Design

**Date:** 2026-08-04
**Status:** Approved (brainstorm with Ryan, 2026-08-04)

## Purpose

Give every Quill component and pattern real usage documentation — when to use it,
what to reach for instead, do/don't rules, and accessibility notes — written once
and delivered to both audiences:

- **AI agents** building apps with Quill (via llms.txt, the registry, generated
  usage pages) so generated UIs follow the system's rules.
- **Portfolio evaluators** reading the deployed Storybook, where the docs double
  as evidence of design-system craft.

Human-facing docs live in the existing Storybook (enriched), not a separate docs
site. That was an explicit decision: one surface to maintain.

## Current state (verified 2026-08-04)

- All 56 top-level component stories have hand-written `docs.description.component`
  blocks (design tokens + usage rules) and `autodocs`.
- All 49 pattern stories have **no** docs — they only render their block.
- `public/llms.txt` (102 lines) is generated by `scripts/build-llms.mjs` from
  registry.json, the token module, and `scripts/registry-intent-tags.mjs`, with a
  CI staleness test. Blocks carry one-line intent + use_when guidance.
- All 54 registry items have an empty/absent `docs` field — the shadcn CLI would
  display that field at install time, but nothing populates it.
- Foundation MDX pages (Colors, Typography, Spacing, Elevation, Tokens, Icons,
  Brand, Introduction, Patterns) exist and are out of scope here.

## Design

### 1. Usage files — the single source

One data module per component and per pattern: `src/usage/<name>.usage.mjs`
(~105 files). Same pattern as `src/tokens/quill.tokens.mjs`: plain `.mjs` so both
Storybook (via Vite) and the node build scripts import the identical object.

Each file exports a `usage` object:

| Field | Contents |
| --- | --- |
| `name` / `kind` | registry name; `component` or `pattern` |
| `summary` | the job, one line |
| `useWhen` | bullets: situations that call for this component |
| `alternatives` | `{ name, when }` — "use X instead when…" cross-links |
| `rules` | do/don't statements, each `{ id, do, dont, visual }`; `id` is stable |
| `a11y` | keyboard behavior, required labels/ARIA, focus expectations |
| `tokens` | design tokens the component consumes |

The block "use when" text currently in `scripts/registry-intent-tags.mjs` moves
into the pattern usage files; the intent-tag module then derives from usage files
so use_when is never written twice.

### 2. Storybook rendering

A shared helper (`src/usage/render.mjs`, importable by stories and scripts alike) formats a usage object into
the markdown that `docs.description.component` accepts. Each story meta replaces
its hand-written block with one line pointing at its usage file. Autodocs stays;
no per-component MDX. Pattern stories gain `tags: ['autodocs']` plus the same
one-liner — closing the 49-story gap with identical machinery.

### 3. Do/Don't stays visual

Rule *text* lives in the usage file (machine-readable). The rendered
right-vs-wrong example lives in the story file as a `DoDont` story built with a
shared side-by-side frame component (green "Do" / red "Don't" framing; caption
pulled from the usage file by rule `id`). JSX belongs in stories; words belong in
usage files. An invariant test enforces the pairing (see §5).

### 4. Generated AI-facing outputs

From the same usage files, three generated, committed outputs:

1. **`public/usage/<name>.md`** — one full usage page per component/pattern
   (rules, alternatives, a11y). New generator following `build-llms.mjs` style.
2. **`public/llms.txt`** — keeps its one-line use_when per block and gains a link
   to each item's usage page (llms.txt convention: short index, deeper links).
3. **`registry.json` `docs` field** — compact usage rules injected per item, so
   `npx shadcn add` prints them in the consumer's terminal at install time.

### 5. Drift protection

Same doctrine as build-llms today — generated files are committed, CI fails when
stale:

- Staleness tests for `public/usage/*.md`, `llms.txt`, and the registry `docs`
  fields (extending `build-llms.test.mjs` / `registry-meta.test.mjs` patterns).
- Invariant: every component/pattern story has a usage file — no new component
  ships undocumented.
- Invariant: every rule with `visual: true` has a rendered `DoDont` pair.

No bot changes needed; the existing self-heal/drift-audit system patrols the new
fences automatically once the tests exist.

## Phasing — four PRs, each releasable

Standard flow per PR: branch → PR → CI green → merge, with version bump +
CHANGELOG entry.

1. **Pipeline + 3 pilots** — schema, Storybook renderer, the three generators,
   all tests, and Button + Dialog + the Alerts pattern fully written. Validates the loop
   end-to-end before mass writing.
2. **49 patterns** — seed use_when from the intent-tag file; write summaries and
   rules. Biggest verified gap closed.
3. **56 components** — migrate existing hand-written docs blocks into usage
   files; add useWhen + alternatives.
4. **Do/Don't visuals + a11y notes** — the deepest writing pass, across all
   items.

## Out of scope

- A separate docs site on quilldesignsystem.com (considered, declined).
- Hand-crafted MDX flagship pages (may revisit after Wave 4).
- Figma-side descriptions / Code Connect sync (Code Connect currently blocked).
- Changes to foundation MDX pages.

## Success criteria

- Zero hand-maintained duplicate prose: every usage statement exists in exactly
  one `.usage.mjs` file; every other surface is generated and staleness-tested.
- All 105 stories (56 components + 49 patterns) render usage docs in Storybook.
- Every registry block and component item (blocks, icon, tone-badge — not the
  theme/lib infrastructure items) ships a populated `docs` field.
- An AI agent reading llms.txt can reach full per-component usage guidance in
  one link hop.
